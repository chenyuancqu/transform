# Codex 执行文档：现代高级智慧园区数字孪生 Demo

版本：1.0｜技术栈：Three.js / React Three Fiber｜目标：可运行、明亮通透、精致现代、免费资产优先

## 0. 总任务（请 Codex 从这里开始）

你是负责此仓库的高级 R3F 工程师与 Technical Artist。请在现有项目内实施一个**小型现代高级智慧园区**的数字孪生 Demo。不要再基于原先的积木楼、球形树和十字路口做微调。保留业务层，重建美术展示层。先完成独立高质量样板，验证后再接入完整仿真。

**视觉方向**：现代高级园区，不是低多边形卡通城市，不是夜间赛博朋克。白色/暖白石材、蓝灰玻璃幕墙、金属遮阳构件、鲜活但自然的绿化、石材铺装、晴朗天空、干净通透的日光。适度风格化，不追求照片级路径追踪。

**严格规则**：
1. 先检查仓库和已有资产、版本、业务锚点，不要猜测目录、接口或模型存在。
2. 不得用 BoxGeometry 建造主要建筑来冒充高质量 GLB；基础几何体可用于道路基层、地面、辅助线、碰撞体与调试。
3. 不得下载来源不明或许可不明的模型；需要登录、付费、禁止 AI 处理、授权不清或下载失败时，记录阻塞并等待用户提供文件。不能拿临时方块当完成品。
4. 不得修改无人机任务时序、真实/仿真坐标、路径点、速度、暂停/恢复/重置逻辑与统计含义。
5. 每阶段完成代码、构建、截图、性能测量和报告；没有浏览器能力时明确标记“未视觉验证”。
6. 任何大量修改前先创建可恢复的 Git 分支或提交点，不覆盖用户未提交改动。

**阶段门 G0**：明确哪些是业务数据、哪些是可删除的旧美术代码，且有可恢复基线，才允许改造。

**资产优先级**：主研发楼（最重要）→ 低层调度中心 → 真实树冠树木 → 景观设施 → 地面 PBR 贴图 → 停机坪设施。主楼必须是经过建筑设计的模型：有入口、玻璃分格、遮阳构件、屋顶细节和非纯盒子轮廓。下载后逐个旋转检查四面、顶部、底部、UV、材质及贴图完整性。

## 3. 目标场景规格

小型园区，仅包含：
- 一栋 4–6 层主研发办公楼（视觉中心）；
- 一栋 1–2 层无人机调度中心（与主楼风格统一）；
- 一处中央景观广场（铺装、花坛、灌木、座椅、步道）；
- 1–2 个无人机起降平台（标识、充电设施、安全边界）；
- 一条合理的园区道路及人行道、路缘石；
- 约 12–20 棵有不同姿态的景观树，少量路灯和导视牌。

上述数量是规模建议，不是凑数目标。不要形成孤立的 X 型十字路、突然中断的道路、大面积空草坪或矩形积木沙盘。所有场景摆放围绕建筑入口、行人动线、无人机起降安全区组织。对于与业务相关的坐标和障碍边界，保持既有语义和约束；装饰区域可以重新规划。

默认镜头：斜俯视建筑展示视角，画面主体占据大部分视口，能同时看到主楼、花园和停机坪。另保留高位业务监控视角与用户 Orbit 控制。相机根据场景包围盒和视口比例计算，不写死一个只适用于单一分辨率的构图。

## 4. 实施架构（按实际仓库适配）

建议职责划分：

```
public/assets/campus/
  buildings/  nature/  props/  textures/  drones/
src/scene/
  assets/assetManifest.ts
  components/BuildingAsset.tsx
  components/Landscape.tsx
  components/DronePad.tsx
  CampusPreviewScene.tsx
  CampusProductionScene.tsx
  CampusLighting.tsx
  CampusCamera.tsx
src/simulation/  # 既有业务逻辑保持
src/ui/          # 既有控制面板保持
 docs/campus-baseline.md
 docs/asset-licenses.md
 docs/campus-acceptance.md
```

- 资产清单包含 URL、物理尺寸、朝向、归一化比例、许可标识与用途。统一世界坐标、轴向、单位与落地基准。
- 用 `useGLTF`/`GLTFLoader` 加载真实模型；重复模型复用 geometry/material，静态实例必要时使用 `InstancedMesh`。不应把同一个 `Object3D` 同时挂载多处；按需克隆节点并避免不安全地共享/释放资源。
- `gltfjsx` 可用于资产结构拆分，`glTF-Transform` 可用于优化；不要无差别压缩、破坏 PBR 材质、玻璃透明度或 UV。
- 独立预览入口（例如 `/campus-preview`，根据路由实际情况决定），与旧业务场景并存；最终通过切换接入新场景。
- 设备渲染从原有仿真数据读取 position、heading、state、progress，不要在视觉组件里再实现一套独立的飞行状态机。

## 5. 分阶段任务与验收门

### G1：单栋建筑资产验收

只做主楼独立预览：真实模型、完整 PBR 贴图、自然日光、可旋转相机、中性测试地面。输出正面、斜角、背面、屋顶截图，检查尺寸、材质、面数、draw calls、加载失败情况。若模型仍像盒子楼，淘汰资产，不能靠补窗户与提饱和度掩盖。**G1 不通过，不进入场景扩展。**

### G2：精品样板街区

加入低层调度中心、中央花园、完整道路与步行空间、停机坪及无人机。以建筑入口与道路的空间关系为先，绿化分层布局。视觉标准：高级现代园区、画面丰富但不杂乱、各材质可区分、道路有合理去向。输出相同视口的全景、建筑近景、停机坪近景。

### G3：渲染管线和色彩

检查 `outputColorSpace`、tone mapping、exposure、环境光、主方向光、HDRI、fog、后期、PBR 材质。尊重当前 Three/R3F 版本默认设置，禁止重复 gamma 校正。对比关闭雾/后期与正常效果，避免灰蒙蒙、曝光过度、白墙发灰、草坪荧光绿、玻璃纯蓝塑料感。建议自然晴天日光、柔和接触阴影；Bloom 只用于少量设备状态，不作为建筑美化主要手段。

### G4：接入无人机业务

保持起飞、巡检航点、返航、暂停、恢复、重置、速度、任务状态、统计面板全部正确。飞行路线用克制的青蓝线，设备状态用少量悬浮信息，告警用橙色；轨迹不得穿过实体建筑，若原路径与新装饰几何冲突，应调整装饰物或提交业务约束冲突报告，不能悄悄修改任务坐标。

### G5：性能和最终验收

使用固定环境记录优化前后：稳定 FPS、平均/P95 帧时间、draw calls、triangles、纹理内存估计、资源下载体积、首次加载耗时。桌面目标 60 FPS，但必须基于目标设备实测；不能声称所有设备保证 60 FPS。先排查 JS 主线程、useFrame 状态更新、阴影、DPR、资源加载，再优化模型。静态重复资产实例化，按需减少纹理尺寸、LOD 与可见性；优先保留主建筑的视觉品质。

最终原则：**模型质量决定美术上限，场景设计决定整体观感，R3F 负责交互和实时呈现，数字孪生业务必须准确。**
